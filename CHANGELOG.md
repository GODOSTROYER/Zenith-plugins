# Changelog

## Unreleased: full agent coverage

Needs the matching Zenith backend (whole-workspace grants, link protocol 2 and the workspace coverage tools). Against an older backend everything still works as before: the new tools are simply not listed and `login` falls back to link protocol 1.

**Tools.** `CONTROL_TOOLS` gains twelve reads, all `mutates: false`: `zenith_list_workspaces`, `zenith_get_workspace`, `zenith_list_blueprints`, `zenith_list_secrets`, `zenith_get_alerts`, `zenith_get_audit`, `zenith_investigate`, `zenith_get_health`, `zenith_get_service_logs` (logs scope), `zenith_discover_resources`, `zenith_list_apps` and `zenith_get_handoff`. The write set is unchanged: every new change is a new `kind` of `zenith_prepare_change`, reviewed in the browser. `contracts/control-v2.json` is **not** regenerated in this change, so `npm run contracts:check` fails until it is regenerated from the integrated backend with the new `node scripts/contracts.mjs --write --backend ABS`.

**Link protocol 2.** `LINK_PROTOCOL_VERSION` is 2. `login --workspace ID` sends an unverified `workspaceHint`; `login --new-workspace NAME` sends `workspaceNameHint`, which prefills the approval page's Create workspace panel. The connector accepts a whole-workspace grant (`allProjects: true`, `projectIds: []`, no environment narrowing) and never pins a project for one. A version-1 server's refusal of the version-2 start body triggers one retry in version 1, without hints, and the connector says the hint was not sent.

**Profiles everywhere, switched without a restart.** `login` now writes a named profile on every platform and makes it active. It is named after the workspace slug when Zenith returns one, stepping to `-2`, `-3`, … when taken. On Windows the credential stays a CurrentUser DPAPI vault and the profile lives in `%APPDATA%\zenith\profiles.json`, whose directory and file are created and checked with protected user/SYSTEM-only ACLs by the vault's native helper; `login --print-env` keeps the older environment block, and `logout --vault` removes such a vault. `resolveProfilesFile` no longer excludes Windows. `profile use NAME` switches the active profile, and `list`/`use`/`remove` default to the file the server reads. The stdio server resolves its client per call: when the profiles file's identity, size or modification time changes it loads the new profile, lists its tools, replaces the registered tools and sends `notifications/tools/list_changed`. A profile that cannot be loaded fails closed.

**Skills.** New `workspace`, `environments`, `alerts`, `findings`, `operate` and `secrets` skills; `link`, `connect`, `edit`, `deploy` and `publish` cover whole-workspace links, the new edits (`env.set`, `secret.adopt`, `secret.remove`, `service.scale`), deployment cancel and app suspend/resume. Secret values, provider credentials, alert destinations, policy loosening, deletions, deployment approval and people changes are browser hand-offs through `zenith_get_handoff`. A new test scans every skill and agent for any instruction to ask the user for a secret, password or token, and for tool names the client cannot serve. The two Claude reviewers name the evidence tools a parent workflow can gather; they still have no MCP permission of their own.

## 0.3.0-dev.1

Adds `zenith login`, `zenith logout` and `zenith status`. `login` links this connector to a Zenith account through the user's browser: it prints a verification URL and a user code, opens a browser when it can, and polls the link endpoint honouring the server's interval and `slow_down` until the credential is issued, denied or expired. The issued credential goes into the credential store the platform already had — a private 0600 file beside the named profile on POSIX, the macOS Keychain with `--keychain`, a CurrentUser DPAPI vault on Windows — before anything is printed, and it is never printed. The device code is held in memory only: it reaches no file, no printed line and no diagnostic record.

Local write enablement now follows the scopes the browser granted rather than a second local flag. The browser approval named the workspace, the projects and the scopes under a live signed-in identity, which is a stronger opt-in than `ZENITH_ALLOW_WRITES=1`; the server still hides write tools when its own capability is off, and `zenith_execute_operation` still requires a browser-approved digest. `logout` removes the local credential only — a credential may never revoke itself, so `--revoke` opens the browser page where revocation actually happens. `status` is additive beside `doctor`, whose JSON shape is unchanged, and introduces no MCP tool, so `contracts/control-v2.json` and backend contract parity are untouched.

**Marketplace install, as an explicitly labelled unsigned preview.** The generated packages now declare their own activation mode in `provenance-mode.json` and carry the matching descriptor. The committed shape is `"mode": "unsigned-preview"` with a `.mcp.json` that runs the packaged bridge directly (`node ${CLAUDE_PLUGIN_ROOT}/runtime/bridge/cli.mjs stdio`, `ZENITH_API_VERSION=2`), and the activation gate accepts that declaration — so `/plugin marketplace add GODOSTROYER/Zenith-plugins` plus `/plugin install zenith@zenith` activates with nothing for an operator to configure, where a launcher-invoking descriptor failed closed on inputs no user could supply. In exchange, `login` leads with `unsigned preview build — not publisher-verified`, `status` and `doctor` carry `activation` and `verification`, and the link protocol's client name becomes `Claude Code - unsigned preview` on the approval page. The preview guarantees the integrity of a marketplace fetch and nothing about a publisher; docs/provenance.md#unsigned-preview states the limits in full. The signed-release path is unchanged and is now built explicitly with `npm run build:signed` (which `release:sign` runs for you): it keeps the `zenith-plugin-launcher` descriptor the launcher binds to, and the launcher itself is untouched. Setting `ZENITH_PROVENANCE_MANIFEST`, `ZENITH_PROVENANCE_TRUST` or `ZENITH_REQUIRE_PROVENANCE=1` ignores the marker and verifies any package like a release; a missing or malformed marker still fails closed with `provenance_required`.

With no explicit connection variable set, the v2 connector now reads the named-profile document `login` writes in the user's own configuration directory (`$XDG_CONFIG_HOME/zenith/profiles.json`, else `~/.config/zenith/profiles.json`), POSIX only. A plugin's MCP server is started by the host from a committed descriptor that cannot name a per-user path, so without this a completed browser link could not be used by the next server start. An explicit `ZENITH_PROFILES_FILE` always wins and any explicit connection variable disables the lookup.

New `link` skill, rewritten `connect` skill, and a `deploy` skill plus `zenith-inspector` reviewer that state the phase-1 truth: the `sandbox` provider simulates deployments, and LocalStack and AWS are not enabled yet. `scripts/build.mjs` and `tests/hardening.test.mjs` now run the same scan over every generated package file for an agent bearer, a link device code or a `ZENITH_TOKEN` assignment, so a credential cannot reach a commit through either route. `login` stays behind the activation gate: a command that opens a network connection and writes a credential is the last one that should run before the package has been verified.

## 0.2.0-dev.1

Adds an opt-in maintained-SDK control path, named profiles, Windows DPAPI credential source, local source packaging/upload, eleven workflows, two Claude evidence reviewers, versioned tool contracts and manually attested review artifacts. Requires the companion reviewed-operation backend merged in Zenith PR #6. V1 remains read-only and separately configured. No implicit privilege migration or public release.

Provenance follow-up (breaking for installed packages). The generated MCP descriptor invokes `zenith-plugin-launcher`, which the repository now publishes as its only `bin`; an existing `command: node` registration must be replaced. Inside an installed package `--help` and `--version` remain usable without provenance inputs, while `doctor`, `stdio`, `setup` and the v2 control commands fail closed with the real `provenance_required` code instead of a misleading credential error. The launcher verifies a private staged copy and executes that copy, binds the spawned entry to the signed descriptor, enforces a recorded rollback floor, and refuses world-writable trust inputs. Signed envelopes must now carry an expiry at both sign and verify; the operator CLI defaults it to 90 days. Release signing is a gated operator step that refuses to run in CI, emits per-package envelopes for the activation gate, and re-verifies what it signed. See docs/provenance.md for key custody, rotation and the limits of static revocation.

Integration follow-up: native remote OAuth configuration no longer requires an existing credential. Windows protected credentials handle piped input, Unicode and short-path aliases without weakening private security descriptors. Generated packages are synchronized and checked against shared source.

Private connection setup, strict reader transport, cancellation, diagnostics, five skills, complete package integrity and cross-platform verification. Preserved as the legacy baseline.
